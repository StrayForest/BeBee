# Skill — Competitor Research

Use for player-facing gameplay, UX/UI, progression, art/VFX and onboarding work.

## Required sequence

1. Restate the exact player problem.
2. Read `DECISIONS.md` and relevant BeBee domain doc.
3. Find at least two shipped references when reasonably available.
4. Prefer references that solve the exact problem; do not over-index on one developer.
5. Observe the exact state/flow, not only store descriptions.
6. Record source/platform/date and what is directly observed vs inferred.
7. Measure where possible: actions, timing, HUD count, blocked state, reward timing, mobile behavior.
8. Identify the transferable pattern and the proprietary expression that must not be copied.
9. Produce a short recommendation and unresolved questions before implementation.
10. Feed the result into `docs/templates/feature-research.md`.

## Do not

- copy maps, art, sounds, text, proprietary code or exact distinctive layouts;
- treat popularity as proof that every feature is good;
- use open-source architecture as visual/UX authority;
- write code before the research conclusion exists.
